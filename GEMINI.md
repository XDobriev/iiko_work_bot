## 1. Что это за проект

Telegram-бот ресторана **«Бейни»**. Принимает фото или голосовое сообщение с закупкой, распознаёт его (Gemini), сверяет цены с историей, показывает карточку в Telegram и по кнопке **«Создать в iiko»** создаёт в iikoWeb **приходную накладную-черновик**. Проводит накладную человек в iikoWeb.

Стек: Node.js 24, TypeScript (ESM, `NodeNext`), `grammy` (Telegram), встроенный `node:sqlite`, `zod`, `dotenv`. Тестового фреймворка нет.

### Карта файлов

## 2. Жёсткие правила (нарушать нельзя)

### Секреты и данные
1. **Никогда не выводи, не логируй и не коммить** содержимое `.env`: ключи Gemini, токен Telegram, пароль iiko. Читая `.env`, показывай только имена переменных.
2. Не добавляй `.env`, `data/`, `*.db` в git. Они уже в `.gitignore`.
3. В `.env` должна быть **одна** строка `IIKO_PASSWORD`. При дублях `dotenv` берёт последнюю, а человек читает первую, и возникает путаница.

### iiko — боевая система
4. iiko — это **настоящая учётная система ресторана**. Любой тест отправки создаёт там реальный документ.
5. Не отправляй ничего в iiko без прямого указания пользователя. Тест отправки — только с явной пометкой «ТЕСТ» в комментарии накладной и с последующим удалением (см. раздел 6).
6. **Не добавляй в бота автоматическое проведение накладных** без явного запроса. Сейчас бот создаёт только `DRAFT`, и это намеренная защита от ошибок распознавания.
7. Не используй `git push --force`, не коммить и не пушь, пока пользователь об этом не попросил.

### Код
8. Это **ESM**: в относительных импортах всегда пиши расширение `.js` (`import { x } from './file.js'`), даже если файл на диске `.ts`.
9. Используй `node:sqlite` (`DatabaseSync`), а не `sqlite3`, `better-sqlite3` и т. п. Не ставь новые зависимости без согласования.
10. Весь текст, который уходит в Telegram с `parse_mode: 'HTML'`, и **любые данные от нейросети или пользователя** оборачивай в `escapeHtml()` из `src/bot/formatter.ts`. Невыключенные символы `<`, `&` ломают отправку сообщения.
11. Любой ответ Gemini проходи через zod-схему `InvoiceDataSchema`. Не используй `any` и не обращайся к полям ответа напрямую.
12. Не меняй схему БД «на месте». Новые колонки добавляй через список `requiredColumns` в `src/db/database.ts` (миграция через `ALTER TABLE ... ADD COLUMN`), чтобы существующая база `data/invoices.db` не сломалась. Не удаляй колонки и не пересоздавай таблицы.
13. Не переименовывай файлы и не меняй структуру папок «для красоты». Меняй только то, что нужно для задачи.
14. Не удаляй существующие проверки и обработку ошибок ради краткости. Не оставляй `TODO`, заглушки и закомментированный код вместо реализации.

## 3. Как работать (порядок действий)

1. **Прочитай** файлы, которые будешь менять, и файлы, которые их вызывают (`grep` по имени функции). Не правь код по памяти.
2. **Сформулируй план** в 3–6 пунктах и покажи пользователю перед крупными изменениями (больше одного файла или любое изменение схемы БД, промпта, iiko-клиента).
3. **Меняй минимально.** Одна задача — один набор правок. Не рефакторь соседний код.
4. **Проверь типы**: `npx tsc --noEmit` должен завершаться без ошибок. Не говори «готово», пока не запустил эту команду.
5. **Проверь поведение**, а не только сборку: запусти `npm run test:pipeline` или напиши короткий скрипт и покажи его вывод.
6. **Отчитайся честно**: что изменено, что проверено и как, что **не** проверено. Если проверить не удалось (нет ключа, нет доступа) — так и напиши. Не утверждай, что что-то работает, если ты это не запускал.
7. Если требование неясно или может повлиять на реальные данные ресторана — **спроси пользователя**, а не угадывай.

### Команды

```bash
npm run dev            # запуск с автоперезагрузкой
npm start              # запуск (после npm run build)
npm run build          # сборка в dist/
npx tsc --noEmit       # проверка типов (обязательна перед «готово»)
npm run test:pipeline  # ручной прогон БД, парсера, форматтера, Gemini
```

Запуск скриптов вне папки проекта: используй расширение `.mts` и абсолютные `file:///` импорты, иначе `tsx` соберёт файл как CommonJS и упадёт на top-level `await`.

Платформа — **Windows**. Пути содержат кириллицу (`C:\Учеба\Бизнес-проекты\iiko-bot`), всегда заключай их в кавычки. Для переносов строк git предупреждает про CRLF — это нормально.

## 4. Интеграция с iikoWeb — как устроено и как не сломать

Подробности и результаты проверки: раздел «Интеграция с iikoWeb» в `README.md`. Кратко:

* Клиент `src/iiko/client.ts` работает через **внутренний API iikoWeb** (`https://beyni.iikoweb.ru/api/...`) с cookie-сессией. Это не iiko Cloud API и не iikoServer API. Адреса `/api/1/access_token` и `/resto/api/...` на этом сервере **не существуют** — не возвращай их.
* Порядок: `POST /api/auth/login` ➔ справочники ➔ `POST /api/documents/product/ids` ➔ `POST /api/documents/create` (`status: DRAFT`) ➔ `POST /api/documents/save/{id}` ➔ `GET /api/auth/logout`.
* **Всегда отправляй заголовок `Accept-Language: ru-RU`** (константа `BASE_HEADERS`). Сервер возвращает 500 на `Accept-Language: *`, который Node подставляет сам. Это самая частая причина «внезапной» ошибки входа.
* Поставщик не найден в iiko ➔ накладная не создаётся (это правильно). Товар не найден ➔ позиция пропускается и попадает в `unmatched`, бот показывает предупреждение.
* Хочешь добавить действие (проведение, удаление, чтение) — **не придумывай адрес**. Попроси пользователя открыть iikoWeb в Chrome, выполнить действие вручную и прислать запрос из вкладки Network (адрес, тело, ответ), либо используй доступный инструмент браузера и посмотри запрос сам.

Известные адреса: чтение `GET /api/documents/get/{id}?type=INCOMING_INVOICE`, список `GET /api/documents/list?...`, удаление `POST /api/documents/update_status/{id}` с `{"status":"DELETED","type":"INCOMING_INVOICE"}`. Запрос проведения **ещё не изучен**.

## 5. Что нужно исправить (известные слабые места)

Приоритет: **P1** — исправить в первую очередь, **P2** — важно, **P3** — когда будет время. Перед каждым пунктом уточняй у пользователя, если он затрагивает поведение для персонала.

### 5.1. Распознавание Gemini (`src/gemini/recognizer.ts`) — главный источник проблем

Модель Gemini как распознаватель даёт нестабильный результат на рукописных накладных, а API периодически отвечает 503/429. Что исправить:

* **P1. Нет схемы ответа.** Сейчас в запросе только `responseMimeType: 'application/json'`, а структура описана словами в промпте. Добавь `responseSchema` в `generationConfig`, чтобы модель не возвращала лишние поля и не путала типы. Валидацию через zod при этом оставь.
* **P1. Список моделей зашит в коде** (`getCandidateModels`). Там жёстко перечислены `gemini-3.5-flash-lite`, `gemini-3.5-flash`, `gemini-3-flash-preview`, а `gemini-3.8-flash` исключён «на время сбоя». При этом значение по умолчанию в `config.ts` — `gemini-3.8-flash`, в `.env` — другая модель, а README и комментарии говорят «3.8». Нужно: вынести порядок моделей в конфиг (`GEMINI_MODELS` через запятую), убрать исключение, привести README, логи и комментарии в соответствие с реальностью. Не выдумывай названия моделей: актуальные берись из документации Google или спрашивай у пользователя.
* **P1. Не повторяется ответ с невалидным JSON.** Если модель вернула битый JSON, `JSON.parse` падает, и цикл переходит к следующей модели без повтора. Добавь один повтор на той же модели при ошибке разбора.
* **P2. Ключ API передаётся в URL** (`?key=...`) и может попасть в логи. Передавай его заголовком `x-goog-api-key`.
* **P2. Год «2026» зашит в промпте.** Подставляй текущий год из `new Date()`.
* **P2. Тип изображения зашит как `image/jpeg`.** Фото из Telegram обычно JPEG, но определяй тип по данным или передавай явно.
* **P2. Промпт слишком общий для рукописного текста.** Добавь в промпт правила для типичных ошибок: перепутанные «1»/«7», запятая и точка в десятичных дробях, сокращения («кг», «шт», «уп»), слитно написанные количество и цена. Проверяй гипотезы на реальных фото, а не «на глаз».
* **P3. Нет метрики качества.** Заведи небольшой набор эталонных накладных (фото + правильный JSON) в `tests/fixtures/` и скрипт, который сравнивает ответ модели с эталоном. Без него любое изменение промпта — вслепую.

### 5.2. Сопоставление названий с номенклатурой iiko (`src/iiko/client.ts`)

* **P1. Нечёткое совпадение «по вхождению» (`findByName`) может выбрать не тот товар**: для «Сыр» подойдёт любая позиция, содержащая слово «сыр», и победит самое короткое название. Нужен нормальный алгоритм: сначала точное совпадение, потом поиск по токенам с порогом схожести, а при неоднозначности — **не угадывать, а спросить человека в Telegram** (кнопки с вариантами).
* **P1. Таблица `product_mappings` уже есть в БД (`src/db/database.ts`), но нигде не используется.** Реализуй запоминание выбора человека: «рукописное название ➔ товар iiko». Это уберёт большинство ошибок при повторных закупках.
* **P2. Единица измерения берётся из карточки товара iiko, а не из накладной.** Если в накладной «2 банки», а в iiko товар в кг, количество будет неверным. Нужна проверка и предупреждение при расхождении единиц.
* **P2. Непринятые позиции пропускаются.** Сейчас бот сообщает об этом, но накладная в iiko получается неполной. Реши вместе с пользователем: блокировать создание, пока все позиции не сопоставлены, либо создавать с предупреждением.

### 5.3. Бот и данные

* **P2. Проверка дубликатов слишком грубая** (`checkDuplicate` в `src/db/invoices.repo.ts`): две разные накладные одного поставщика за один день считаются дубликатом. Добавь сравнение итога и состава позиций.
* **P2. `src/bot/bot.ts` — 630 строк с вложенными `if (action === ...)`.** Разбей обработчик кнопок на отдельные функции по действиям, не меняя поведение. Делай это отдельным коммитом, после проверки.
* **P2. Сессии редактирования (`activeEditSessions`) хранятся в памяти** и теряются при перезапуске. Если пользователь в середине правки — потеряет ввод. Либо храни в БД, либо явно сообщай о сбросе.
* **P3. Нет автоматических тестов.** Минимум: тесты `parseInvoiceEditText`, `normalizeName`, `compareWithHistory`, `findByName` на встроенном `node:test`, без новых зависимостей.
* **P3. Права доступа iiko.** Сейчас бот входит под учётной записью администратора. Для боевого режима заведи отдельного пользователя только с правами на просмотр и создание черновика приходной накладной (`DOCUMENT_BUNDLE_INCOMING_INVOICE_VIEW`, `..._CREATE_AND_EDIT_DRAFT`) — без права проведения.

### 5.4. Порядок и документация

* **P3.** В `.env` есть дубль `IIKO_PASSWORD` и устаревший комментарий «iiko Cloud API» — почисти (без вывода значений).
* **P3.** Положи в репозиторий `.env.example` с именами переменных и пустыми значениями.
* **P3.** Добавь `.gitattributes` (`* text=auto`), чтобы убрать предупреждения про CRLF.
* **P3.** Устаревшие `bot.py` и `requirements.txt` — предложи пользователю убрать из репозитория. Не удаляй сам.

## 6. Безопасный тест отправки в iiko

Если пользователь просит проверить отправку:

1. Убедись, что в `.env` задан `IIKO_PASSWORD`.
2. Отправляй накладную с пометкой «ТЕСТ» в `notes`. Реальный поставщик и товар должны существовать в iiko, иначе накладная не создастся.
3. Запусти тест с `IIKO_TEST_SEND=1`. В PowerShell: `$env:IIKO_TEST_SEND='1'; npm run test:pipeline`, в Git Bash: `IIKO_TEST_SEND=1 npm run test:pipeline`. Либо напиши короткий скрипт с `IikoClient.createInvoice`.
4. Прочитай созданный документ обратно (`GET /api/documents/get/{id}?type=INCOMING_INVOICE`) и сравни статус, поставщика, склад, позиции, суммы.
5. **Удали тестовый документ** (`update_status` ➔ `DELETED`) и проверь, что его нет в списке. Только удаляй документы, которые создал сам, проверив номер, статус `DRAFT` и пометку «ТЕСТ».
6. Сообщи пользователю номера созданных и удалённых документов.

## 7. Чего не делать (частые ошибки агентов)

* Не «исправляй» то, о чём тебя не просили, и не переписывай файл целиком ради одной правки.
* Не придумывай адреса API, имена моделей, поля БД и функции — проверяй по коду и документации.
* Не оставляй код, который не запускал. Если не смог проверить — напиши об этом.
* Не отключай строгий режим TypeScript (`strict`) и не добавляй `@ts-ignore` / `any` для обхода ошибки типов.
* Не меняй формат карточки и тексты бота без согласования: ими пользуются сотрудники ресторана.
* Не отправляй в Telegram сообщения без `escapeHtml` для динамических данных.
* Не запускай продолжительные процессы (`npm run dev`) в переднем плане без необходимости. Бот работает через long polling, второй экземпляр с тем же токеном вызовет конфликт `409`.
